# Prompt para Claude Code — CC Creator v2

## Contexto del proyecto

CC Creator es una PWA que permite estructurar ideas de producto desde el móvil y generar un documento markdown (CLAUDE.md) listo para usar como brief de un POC. La versión anterior usaba nodos visibles (Conversación, Definición, Referencia, Proceso, Diseño) que el usuario llenaba manualmente. Vamos a rediseñar el flujo de captura, cambiar el rol del MCP, y actualizar la estructura del documento generado.

---

## 1. Nuevo flujo de captura: idea libre + cuestionario guiado

**Objetivo:** eliminar la fricción de llenar múltiples formularios estructurados en móvil. El usuario solo hace dos cosas activamente: contar su idea libremente, y responder un cuestionario de opción múltiple.

### Paso 1 — Campo único de idea libre
- Reemplazar el flujo guiado de 5 nodos por **una sola interfaz** donde el usuario escribe (o dicta por voz) su idea libremente, sin estructura, tal como se le ocurra.
- Este texto libre es el único input manual que el usuario redacta desde cero.

### Paso 2 — Cuestionario de selección múltiple generado por IA
- A partir del texto libre, la IA (vía MCP, ver sección 2) genera un cuestionario corto de preguntas de **opción múltiple** diseñado para extraer, sin ambigüedad, la información que antes vivía en los nodos de Definición, Proceso, Diseño y Referencia.
- Las preguntas deben ser específicas y accionables, evitando abrir campos de texto libre — el objetivo es que responder sea tan rápido como tocar botones, no escribir.
- Ejemplos de tipo de pregunta: alcance ("¿Cuál de estos incluye tu POC?" con opciones múltiples), exclusiones ("¿Cuál de estos NO debería estar en la primera versión?"), flujo principal ("¿Cuál de estos pasos describe mejor el camino principal del usuario?"), estilo visual (selección entre paletas/referencias sugeridas).
- El cuestionario debe sentirse corto (apuntar a completarse en menos de un minuto). Si la idea es simple, generar menos preguntas; si es compleja, generar más — no un número fijo.

### Nodos: ahora invisibles por defecto
- La estructura de 5 nodos (Conversación, Definición, Proceso, Referencia, Diseño) se mantiene **como modelo de datos interno**, poblada automáticamente con las respuestas del texto libre + cuestionario.
- El usuario **no ve los nodos** en el flujo principal. Solo se muestran si el usuario entra explícitamente al "modo avanzado / canvas libre" (funcionalidad existente, sin cambios) para revisar, editar o conectar nodos manualmente en estructuras no lineales.

### Semáforo de calificación (se mantiene, aplicado sobre los nodos ya poblados)
Antes de generar el documento final, evaluar el resultado (ya completado automáticamente por el cuestionario) contra estos 6 criterios y mostrar un semáforo con retroalimentación accionable:

1. **Claridad del problema** — ¿Se explica qué dolor resuelve, no solo qué hace?
2. **Alcance delimitado** — ¿Hay tanto qué incluye como qué excluye explícitamente?
3. **Flujo de usuario mínimo** — ¿Existe al menos un camino feliz (happy path) definido?
4. **Dependencias externas sin resolver** — Detectar integraciones complejas (pagos, auth social, servicios de terceros) no marcadas como fuera de alcance Fase 1; genera advertencia, no bloqueo.
5. **Coherencia entre respuestas** — Sin contradicciones entre lo que pide diseño/proceso y lo que excluye el alcance.
6. **Tamaño estimado del POC** — Estimación aproximada de complejidad/tiempo (ej. "medio día", "1-2 días", "más de una semana — considera recortar alcance"), mostrada como señal, no bloqueo.

Si algún criterio queda incompleto tras el cuestionario, la app debe generar 1-2 preguntas adicionales de seguimiento dirigidas específicamente a ese criterio, antes de mostrar el semáforo final — no dejar el hueco sin intentar resolverlo primero.

**Regla de bloqueo:**
- Los criterios 1 (claridad del problema) y 2 (alcance delimitado) son los únicos que pueden **bloquear** la generación del documento — si no se cumplen, el botón de generar/construir permanece deshabilitado hasta resolverlos.
- Los criterios 3, 4, 5 y 6 son **advertencias no bloqueantes**: se muestran en el semáforo con su mensaje accionable, pero el usuario puede ignorarlas y generar el documento de todas formas.

### Edición desde el canvas libre sin perder conexiones automáticas
- Los nodos poblados automáticamente por el cuestionario ya vienen con sus conexiones generadas en el orden lógico del flujo.
- Si el usuario entra al modo avanzado / canvas libre para editar el contenido de un nodo, **las conexiones automáticas existentes deben mantenerse intactas** — editar el texto de un nodo no debe romper ni resetear sus enlaces.
- El usuario puede añadir conexiones adicionales manualmente (estructuras no lineales) sin afectar las que ya existían.

### Gesto de conexión manual (canvas libre) — estilo FigJam / Freeform
- Para conectar dos nodos manualmente en el canvas libre, el gesto debe ser: mantener presionado sobre el borde del nodo origen y arrastrar hasta el nodo destino, soltando para crear la conexión.
- Debe incluir snapping automático al acercarse a un nodo válido como destino, con feedback visual (resaltado del borde) antes de soltar.
- Este gesto reemplaza cualquier modo o botón separado de "Conectar" que requiera selección previa de dos nodos — la conexión se hace en un solo movimiento continuo, sin pasos intermedios.

## 2. Cambio de rol del MCP: motor de procesamiento, no creador de proyecto

**Objetivo:** el MCP deja de conectar el móvil a un proyecto específico de Claude Code para generar código directamente. En su lugar, se usa el procesamiento de Claude Code (corriendo en la Mac del usuario) como motor de inteligencia para generar el documento markdown.

- El flujo ya **no crea ni inicializa ningún proyecto de código** desde el móvil.
- La llamada vía MCP a Claude Code se usa para: generar el cuestionario de opción múltiple (paso 1.2), evaluar los criterios del semáforo, y redactar el CLAUDE.md final con buena calidad de escritura.
- El resultado de este procesamiento es siempre un **documento**, nunca una acción sobre un repositorio o proyecto.
- Mantener dos rutas de procesamiento, seleccionables por el usuario o por configuración de cuenta:
  - **Ruta gratuita (MCP + Claude Code local):** requiere que el usuario tenga Claude Code CLI instalado y su propia suscripción activa; el procesamiento ocurre a través del MCP hacia su Mac.
  - **Ruta de pago (API propia):** para usuarios sin Claude Code instalado; el procesamiento usa la API de Anthropic con clave propia de Kitifica, y se cobra según consumo de tokens.
- Documentar claramente en la UI, de forma visible y constante (no solo en un mensaje puntual), cuál ruta está activa y por qué — ej. una etiqueta persistente tipo "Usando tu Claude Code local" vs "Procesado con nuestra IA — plan de pago" — para que el usuario nunca tenga dudas de qué está pagando o no en un momento dado.

---

## 3. Entrega del documento: copiar y compartir

**Objetivo:** dar flexibilidad total de cómo el usuario saca el markdown de la app.

- Al terminar de generar el CLAUDE.md, ofrecer explícitamente:
  - **Copiar texto** al portapapeles (para pegar donde sea: chat, notas, terminal).
  - **Compartir archivo** usando el share sheet nativo del sistema operativo (iOS/Android), permitiendo enviarlo por WhatsApp, AirDrop, Files, email, etc.
- Ambas opciones deben estar disponibles simultáneamente, no una u otra — el usuario elige según el contexto en que esté.

---

## 4. Estructura de dos fases en el CLAUDE.md generado

**Objetivo:** que el documento final esté explícitamente delimitado a un POC funcional, sin que la IA en la Mac intente construir una aplicación completa.

El CLAUDE.md generado debe incluir siempre estas dos secciones:

### Fase 1: Ejecución inmediata (POC)
- Instrucción explícita: construir solo el núcleo funcional (happy path) descrito en las respuestas del usuario.
- Arquitectura simple, preferiblemente local, sin infraestructura pesada.
- Cualquier integración compleja detectada por el criterio 4 debe aparecer aquí como explícitamente **fuera de alcance**, con nota tipo: "Esto se simula/mockea en Fase 1."

### Fase 2: Visión de escalamiento (bloqueada)
- Solo describe **intención**, nunca detalles de implementación técnica.
- Lista lo que se construiría si el POC valida tracción (ej. cobros recurrentes, autenticación robusta, escalamiento de base de datos).
- Debe quedar claro que esta fase **no se ejecuta ahora** — es contexto de hacia dónde va el producto, no una tarea pendiente.

**Regla estricta:** filtrar cualquier detalle técnico que el usuario haya mencionado sobre features de Fase 2 y reducirlo a una sola frase de intención, para evitar que Claude Code en la Mac se desvíe hacia esa complejidad al leer el documento completo.

## Entregable esperado de esta sesión

1. Reemplazar el wizard de 5 nodos visibles por: campo único de idea libre → cuestionario de opción múltiple generado por IA → nodos poblados invisiblemente en el modelo de datos.
2. Mantener el modo avanzado / canvas libre como vista opcional para editar nodos manualmente.
3. Implementar el semáforo de 6 criterios evaluado sobre los nodos ya poblados, con preguntas de seguimiento dirigidas si falta información en algún criterio.
4. Aplicar la regla de bloqueo: criterios 1 y 2 bloquean la generación si no se cumplen; criterios 3-6 son advertencias no bloqueantes.
5. Asegurar que editar un nodo desde el canvas libre no rompa las conexiones automáticas generadas por el cuestionario.
6. Implementar el gesto de conexión manual estilo FigJam/Freeform (mantener presionado + arrastrar + snapping) en el canvas libre, reemplazando el modo/botón "Conectar" anterior.
7. Cambiar el uso del MCP: de "crear/disparar proyecto en Claude Code" a "usar Claude Code como motor de procesamiento para generar el cuestionario, evaluar criterios, y redactar el CLAUDE.md".
8. Mantener dos rutas de procesamiento: MCP + Claude Code local (gratis) vs API propia (de pago), con indicador persistente en la UI de cuál ruta está activa.
9. Agregar opciones de "Copiar texto" y "Compartir archivo" al finalizar la generación del documento.
10. Modificar el generador del CLAUDE.md para que siempre separe Fase 1 (ejecución) y Fase 2 (visión, sin detalles técnicos).
